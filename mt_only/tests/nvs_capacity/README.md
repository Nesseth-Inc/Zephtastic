This offline benchmark compiles the complete pinned Zephyr NVS engine and extracts the unchanged settings `save` and backend-initialization functions. Only flash, kernel mutex and logging boundaries are mocked. Run `python3 -B run.py --zephyr /path/to/pinned/zephyr --output /path/to/review-output`; outputs stay in the specified scratch directory. Omitting `--output` uses `out/` beside the runner.

The NOR model uses 4 KiB erase sectors, four-byte aligned programming, erased bytes `0xff`, and refuses zero-to-one programming. Cases use four sectors for T096 and eight for XIAO, matching the effective settings configuration. It retains nine synthetic name/value pairs: an 80-byte legacy config, two 128-byte M18 config records, two 1492-byte node records, two 84-byte identity records, and two 1752-byte ledger records. No real identity, keys or settings are read.

Each layout undergoes 1200 mixed updates, all-record byte-exact reads after every update, and 64 mounts including the initial mount. A selected garbage-collecting ledger update is then replayed with interruptions before, midway through, and after every write/erase callback. Fresh mount must retain every unrelated value; the uncertain value may be old or new. A subsequent low-level NVS write/readback is checked solely to demonstrate storage continuity. This is not permission to resume an application journal that has latched a write fault.

ASAN/UBSAN passed. Four-sector initial logical free space is 4956 bytes; eight-sector initial logical free space is 21276 bytes. The workload provokes hundreds of erases intentionally to test reuse. These are simulation counts, not measured flash wear or timing. No physical target, scheduler, controller, flash endurance, arbitrary analog brownout, complete sector loss, external erase or credential rollback is qualified by these results.
